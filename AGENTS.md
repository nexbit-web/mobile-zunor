This is an Expo/React Native mobile application. Prioritize mobile-first patterns, performance, and cross-platform compatibility.

## Zunor

Мобільний застосунок Zunor — сервісу замовлення прибирання. Окремий
репозиторій у робочій теці `zunor/` (карта проєктів і спільні правила —
`../AGENTS.md`). **Бекенд — сайт `../web`**: застосунок ходить у його
`/api/*`, вхід — його better-auth. Продукт і причини рішень —
`../web/MANIFESTO.md`, правила сервера — `../web/AGENTS.md`.

- **Нова можливість для сайту й застосунку** — спершу логіка й ендпоінт у
  `../web`, потім екран тут. Своєї бізнес-логіки (розсилка, статуси,
  доступ) застосунок не має: що можна й що видно — вирішує сервер.
- **Запити — лише через `api()` з `src/lib/api.ts`** (cookie сесії в
  заголовку, `credentials: 'omit'`, помилки — `ApiError`), дані — через
  TanStack Query. Свого `fetch` в екранах не пиши.
- **Браузер — лише для dev-перевірки інтерфейсу** (`web.output: single`).
  Там `/api/*` іде на адресу Metro, а `scripts/dev-api-proxy.js` пересилає
  його на сайт; сесія — cookie сайту, не SecureStore. Тому в екранах
  нічого лише-нативного без запасного шляху для web: `Alert.alert` у
  браузері мовчить — питання «так/ні» через `confirmAction()` з
  `src/lib/confirm.ts`.
- **Код сайту не імпортується шляхом `../web/...`** — збірка EAS клонує
  лише цей репозиторій. Потрібне чисте ядро — копія в `src/shared/` з
  поміткою, звідки взято; змінилось на сайті — зміни копію в тій самій
  задачі.
- **Контракт API**: сервер поля лише додає, тож нові поля в типах
  `src/shared/*` — опційні. Старі версії застосунку живуть місяцями.
- **Стилі — Uniwind (`className`, Tailwind 4).** Кольори — лише токени з
  `src/global.css`: подача ClickUp (так попросив власник) — нейтральні
  сірі без відтінку. Темна — графітова (#141414 → картки #222 → #2e2e2e),
  світла — білий фон і ледь сірі картки (#fff → #f6f6f7 → #eaeaed);
  акцент — із сайту. Де `className` не
  дістає (вкладки, шапки, іконки, плейсхолдер) — `useColors()` з
  `src/lib/theme.ts`, а не hex у компоненті. Варіанти `first:`/`last:`
  тут не працюють — рядок отримує проп.
- **Каркас за роллю** (`app/(app)/_layout.tsx`): клієнт — бічна панель
  (`expo-router/drawer`, `components/drawer/*`) і чат із Zunor на весь
  екран, як застосунок ІІ; майстер — нижня панель без «+» (`MASTER_DOCK`; `false` — системні вкладки `NativeTabs`).
  Маршрути спільні; `TabStack` сам ставить кнопку меню (клієнт) і
  дзвіночок (усім). Для свайпу панелі корінь обгорнуто в
  `GestureHandlerRootView`.
- **ПРОТОТИП: нижня панель клієнта** (`CLIENT_DOCK` у `lib/dock.ts`,
  зараз `true`). Власник дивиться, чи так краще. Головна клієнта —
  розмова з Zunor. Розділи («Замовлення · Чати · Сповіщення · Профіль»)
  і розмова — JS-вкладки (`ClientDockShell` в `app/(app)/_layout`,
  `expo-router/js-tabs`): лише в них під час переходу видно обидва
  екрани. «+» панелі — розмова виїжджає знизу поверх розділу; «✕» у
  розмові — вона їде вниз над розділом (тим, де людина була востаннє),
  без попередження: почату розмову без заявки «+» ще 30 хв відкриває
  знову, а не нову (`KEEP_MS`, `setChatKeepable`; лише в памʼяті);
  між розділами — миттєво (`chatScene`, `stillScene`, 350 мс без
  пружини). Пастка: поки йде перехід, попередній екран лишається
  видимим, і на iOS зверху той, що ПІЗНІШЕ в списку вкладок, а не
  новий, — тому розмова остання, а розділи вмикають перехід лише поки
  вона виїжджає (`isChatOpening`); інакше попередній розділ 350 мс
  закривав новий («Замовлення» відкривались із затримкою). У боковій навігації (`Drawer`) так не можна:
  неактивний екран там одразу `display: none`. Розмову-вкладку НЕ
  ховати `href: null`: в expo-router 58 прихована вкладка не може бути
  відкритою — роутер одразу замінює її першою видимою (так «+»
  відкривав «Замовлення»); панель і так наша, лише з чотирма розділами. Бічна панель — лише в
  розмові (`(home)/_layout` → `ClientDrawerNavigator`): у ній тоді лише
  «Ваші заявки», «✎» (анкета AI асистента) на місці профілю й «+». У
  шапці розмови — лише потрібне: ☰ і «✕», після початку розмови ще «⋯»;
  дзвіночка немає. Сама панель — `components/dock/bottom-dock` (`BottomDock`):
  графітова «скляна» пігулка з гранню-відблиском, активна вкладка —
  світла нейтральна капсула й іконка `primary` (акцент лише іконка);
  вибір можна перетягнути — за пальцем іде сіра капсула-«тінь», іконки
  не міняються й вібрації немає, підсвітка їде після відпускання.
  Кінець списків — над панеллю (`DockSpace` → `useContentBottom`).
  Сповіщення — розділ `(app)/alerts` (той самий `NotificationsScreen`,
  що й `/notifications`), тож дзвіночка в шапках розділів немає (у
  «Чатах» — лише пошук); назва розділу в шапці — ліворуч і більша
  (`headerTitleAlign: 'left'` → ScreenHeader, 22 pt жирна). `false`
  повертає все як було (`ClientShell`: бічна панель з усіма розділами).
  Майстер (`MASTER_DOCK`, власник) — та сама панель і ті самі розміри,
  лише без «+» і з вкладками `MASTER_TABS` («Стрічка · Замовлення · Чати
  · Профіль»; `MasterDockShell`, JS-вкладки, перемикання миттєве);
  сповіщення в нього — як і раніше, дзвіночком у шапці. `false` —
  системні вкладки `NativeTabs`, як було.
  Рішення не прийняте — не розвивати прототип далі без власника.
- **Свайп управо з лівої чверті екрана відкриває панель клієнта**
  (`lib/drawer-swipe.ts`, `drawerSwipeZone`: чверть ширини, не менше
  80 pt). Не з будь-якої точки — це власник спробував і відкинув: з
  середини сторінки панель не відкривається. Закрита панель ловить лише
  рух управо (`openOnRightSwipe` у `configureGestureHandler`: від 8 pt,
  не крутіше 45°; уліво — відмова, хай гортається список), відкрита —
  звичайний жест в обидва боки (стан — із події `state` навігатора).
  Горизонтальні списки, яким свайп управо зараз потрібен, звужують зону
  до краю (`DRAWER_EDGE` = 48 pt): `SwipeTabs` не на першому розділі
  (`useDrawerEdgeOnly`), стрічки підказок, кнопок-відповідей і фото
  Zunor, прогорнуті від початку (`useRowSwipeGuard`). Лише поки їхній
  екран у фокусі — панель тримає й сховані екрани. **Горизонтальні
  списки обгорнуті в `ui/yield-to-drawer.tsx`** (`Gesture.Native()` +
  `requireExternalGestureToFail` жесту панелі, `useDrawerPan`): родна
  прокрутка iOS інакше забирала свайп управо собі навіть на першому
  розділі, де гортати нікуди, і панель на «Замовленнях» і в «Чатах» майже
  не відкривалась, щойно палець потрапляв на перемикач чи картку. Тепер
  список чекає, поки жест панелі відмовиться (уліво, вертикально чи поза
  зоною — одразу). Новий горизонтальний список у розділах клієнта —
  теж у `YieldToDrawer` і з `useRowSwipeGuard`. Типи `configureGestureHandler`
  у expo-router — новий `PanGesture` gesture-handler 3, а приходить
  старий будівник `Gesture.Pan()` (тому приведення до `LegacyPanGesture`).
- **Дзвіночок сповіщень** (`components/header-bell.tsx`) — праворуч у
  шапці майже кожного екрана (так попросив власник): розділи `TabStack`,
  заявка, налаштування та їхні розділи, розмова з Zunor. Немає — на самих
  сповіщеннях, у розмові (там праворуч фото співрозмовника) і в розділах
  налаштувань із кнопкою в шапці («Змінити», «Зберегти»: профіль, AI
  асистент) — там він зайвий. Екрани поверх —
  `WITH_BELL` у `app/_layout.tsx`; свій `headerRight` («⋯», фільтр) —
  через `<WithBell>`, інакше дзвіночок зникне: він завжди останній, біля
  краю. Сповіщення вже нижче в стеку — дзвіночок повертає до них, а не
  відкриває ще одні. Непрочитані — червоний кружечок із числом
  (`RoundButton badge`), лічильник — `useUnreadCount()` (один кеш
  `['badges']` і для бічної панелі). Бічні місця шапки однакові й не
  вужчі за вміст (ScreenHeader міряє), тож назва лишається по центру.
- **Профіль майстра** — `components/settings/master-profile.tsx` (маршрут
  той самий, `settings/profile`, гілка за роллю). Дані —
  `GET /api/me/master-profile`, запис — `POST /api/profile/master`, як на
  сайті: сервер (`saveMasterProfile`) перевіряє все й ставить повторну
  перевірку. Варіанти відповідей і межі — `shared/masters.ts`, копія
  `masters/meta`, `geo/travel`, `cleaning/skills` і `username` сайту:
  міняється анкета там — міняй тут. Фото профілю зберігається одразу,
  приклади робіт — лише разом із формою; нові незбережені при
  «Скасувати» прибираємо з хмари (`discardPortfolioPhoto`).
- **Чати** — `components/chat/*`, як на сайті (`web/…/components/chat`) і
  в Telegram. Список — `chat-list.tsx` (вкладка «Чати»), розмова —
  `app/chat/[id].tsx` → `chat-screen.tsx`, у корені, поверх вкладок: так
  у розмові немає нижньої панелі. Правила:
  - **Список — два розділи `SwipeTabs`** (як «Замовлення»): «Усі» й
    «Непрочитані» (число — непрочитані повідомлення, як на вкладці
    внизу). Дані одні (`['chats']`), розділ — фільтр на місці. Лінія між
    рядками — hairline кольору `input`, від початку тексту: `border` (7%)
    власник не бачив (`ChatSeparator`).
  - **Пошук** — лупа в шапці перед дзвіночком (`WithBell`), як у Telegram
    iOS: шапка плавно гасне (`headerAway` у `lib/large-title`, ScreenHeader
    бере з нього прозорість), на її місці виїжджає `ChatSearch`: поле на
    всю ширину й кругла «✕» праворуч, клавіатура одразу. Згаслу шапку
    потім прибираємо (`headerShown: false`), інакше вона перехоплює
    дотики. Поява й зникнення — `SEARCH_TIMING`, 360 мс рівно: коротше
    власникові здавалось різким. Нижче — один список
    (`searchChats`: спершу імʼя чи @імʼя, далі останнє повідомлення).
    Лежить ПОВЕРХ розділів — «✕» повертає туди ж, де були.
    Android «назад» закриває пошук.
  - **Чисте ядро — копія сайту** в `shared/chat.ts` (типи, реакції,
    емодзі, linkify, час). Набір реакцій закритий — міняється разом із
    сайтом, інакше сервер відхилятиме нові.
  - **Повідомлення — одне сховище за id** (`use-chat-messages.ts`), а не
    сторінки React Query: свіжа сторінка перепитується й «їде», старіші
    довантажуються від найстаршого відомого id — дірок немає.
  - **Живий канал — `private-chat-{id}`** (`useChannel` у chat-screen):
    message:new / edit / delete / reaction / preview / read і
    client-typing («друкує…», і ми шлемо його не частіше 2,5 с) — ті самі
    події, що на сайті. Перепит лишився лише як запасний шлях: поки
    підписка на канал розмови не пройшла (`useChannelLive`) — повідомлення
    раз на 4 с, шапка — 10 с; з каналом шапку («у мережі» подією не
    приходить) — раз на 30 с.
  - **Шпалери** — `chat-background.tsx`, малює Skia (Canvas): узор із
    рядка `chat-pattern.ts` (ЗГЕНЕРОВАНО з `web/static/chat-pattern.svg`)
    розбирається нативно один раз — тому стоїть із першого кадру
    (через expo-image SVG зʼявлявся із затримкою). Світла — як на сайті:
    градієнт Telegram (той самий drawMesh, рахується в коді) і узор у
    шарі soft-light 50%. Темна — тло як є, а САМІ лінії пофарбовані
    градієнтом, як темні шпалери Telegram (`MESH_DARK`: рожевий, синій,
    фіолетовий, персиковий — той самий drawMesh; srcIn у шарі),
    приглушено (`PATTERN_DARK_ALPHA`, 0.38). Від акценту НЕ залежить
    (власник; раніше лінії були рівно кольору акценту). Градієнт «унизу
    яскравіше» власник попросив прибрати. У браузері — `chat-background.web.tsx` (картинками: Skia там
    потребує CanvasKit). Узор застосунку = узор сайту + знак Zunor
    контуром на місці 6 малюнків і кіт-маскот, що лежить на пузі, на
    місці 2 великих (власник: «у тому ж стилі, лініями»):
    `scripts/chat-pattern.py` розбирає шляхи на малюнки, вибирає
    підходящі подалі один від одного й від країв плитки, прибирає їх і
    ставить знак (обведений тією ж товщиною, `LINE`) і кота. Кота
    (`scripts/chat-pattern-cat.txt`) готує `scripts/chat-pattern-cat.py`
    з `mascot/cat-love.source.json` (кадр 0, без сердечок): Chrome
    малює кадр lottie-web, темні контури маскота обводяться в шлях тієї ж
    товщини — запускати лише коли міняється сам кіт. Змінився узор на сайті —
    `python scripts/chat-pattern.py` (перевірити: `--list`, `--preview
    файл.svg`); скопіюй і файл сайту в `assets/images` (web — там знаків
    немає). На сайті узор без знаків, доки власник не попросить.
  - **Skia малює SVG у його власному розмірі** (1440 px), а не в
    прямокутнику `ImageSVG` — плитку масштабуємо `Group transform`. Без
    цього узор виходив утричі більшим і «жирним».
  - **Шапка — звичайна ScreenHeader** (`headerTitle`-функція: імʼя +
    «у мережі»; праворуч фото). Тло — **тверде, з чітким краєм**
    (`headerBlurEffect` → `ui/backdrop.tsx`: розмиття + колір фону
    ~70%), а не тане, як на решті екранів: «тануча» шапка в розмові
    власникові не сподобалась,
    **поле вводу — смуга внизу** (скріпка й капсула на `shell`, кругла
    «Надіслати» кольору акценту). Варіант «окремими скляними блоками, як
    у Telegram» власник спробував і попросив повернути як було.
  - **Клавіатура — `useAnimatedKeyboard`**, не KeyboardAvoidingView:
    висота під полем = max(клавіатура, панель емодзі, смужка «додому») з
    UI-потоку, тож поле їде за клавіатурою кадр у кадр в обидва боки (з
    KAV донизу воно «падало»). Панель емодзі лежить ПІД клавіатурою й
    зникає через ~260 мс після фокусу поля — заміна без стрибка. Дотик
    будь-де в розмові ховає панель (власник: вона «висіла»); без
    клавіатури панель виїжджає й ховається плавно (`floorY`, 260 мс), а
    замість клавіатури — одразу, щоб між ними не було «провалу». Іконка
    смайлик ↔ клавіатура переходить плавно (`EmojiKeyboardIcon`).
  - **Після надсилання поле порожнє** (`lib/input-reset.ts`, обидві
    розмови): iOS-клавіатура з «позначеним» словом (автовиправлення,
    підказка) не приймала `value = ''` чи дописувала слово назад, і текст
    лишався (власник). `reset()` чистить нативно (`clear()`, і ще раз за
    мить), `isEcho()` на початку `onChangeText` відкидає «відкат» у
    перші ~400 мс. Нові поля надсилання — так само.
  - **Без «гумових» анімацій** (пружин, підстрибувань, «вискакування»)
    — власник прямо просив їх прибрати. Лише рівний timing. Поява й
    зникнення цілих шарів (пошук) — повільно, ~350 мс: 150 мс він назвав
    різким.
  - **Своє надіслане — оптимістично** (`Outgoing` у chat-screen): одразу
    в розмові з годинником, підтверджене — заміна на справжнє, ні —
    червоний знак і «Надіслати ще раз». Правка, видалення, реакції —
    теж одразу, з відкатом, якщо сервер не прийняв.
  - **✓✓ — від `peerLastReadAt` співрозмовника** (і `isRead`), не від
    мого lastReadAt. Прочитано — `POST /api/chats/[id]/read`, щойно на
    екрані нове від співрозмовника; лічильник у списку гасимо одразу.
  - **Перевернутий FlatList**: `paddingBottom` контейнера — це ВЕРХ
    екрана (під шапкою). Порожній стан — лише в обгортці `<View>`:
    список розвертає його через `style`.
  - **Число на вкладці «Чати»** (`NativeTabs.Trigger.Badge`) — лише коли
    є непрочитані; нуль — `<Badge hidden />` без тексту. expo-router з
    текстом ігнорує `hidden`, і вкладка світила червоний «0».
  - Чат створюється лише кнопкою «Написати» на картці замовлення
    (`POST /api/orders/[id]/chat`, як на сайті), а не сам.
- **Живий канал (Pusher)** — `lib/realtime.ts`, той самий Pusher, що на
  сайті, і ті самі канали й події. Одне зʼєднання на застосунок:
  `RealtimeBridge` у каркасі `(app)` піднімає його після входу й закриває
  з виходом. Ключ — з сайту (`GET /api/pusher/config`), не з `.env`:
  застосунок бере ключ того сайту, до чийого API ходить. Приватні канали
  підписує `POST /api/pusher/auth` — лише через наш `api()` (cookie з
  SecureStore), `customHandler` у channelAuthorization. Правила:
  - **Подія одразу міняє кеш, без запиту до сайту** — як стори сайту.
    `chat:update` → `applyChatUpdate` (`chat/use-chats.ts`, копія
    handleChatUpdate з `chat-store`): рядок нагору з новим текстом, +1
    непрочитаних, якщо писав співрозмовник і розмова не відкрита
    (`setOpenChat` у chat-screen). `chat:read` → `applyChatRead`:
    співрозмовник прочитав — ✓✓ у списку (і в кеші шапки розмови); я
    прочитав на іншому пристрої — лічильник гасне (якщо після цього не
    прийшло нове). `notification:new` → +1 у `['badges']`,
    стрічка перепитується, лише якщо вона на екрані. Своє надіслане —
    теж `applyChatUpdate` (сервер шле chat:update лише співрозмовнику).
    Раніше подія лише інвалідувала кеш, і число на вкладці чекало ще
    один запит до Vercel — секунди, «телефон повільний». Невідомий чат —
    перепит списку.
  - **Тло — зʼєднання закриваємо, повернення — відкриваємо** (AppState у
    `realtime.ts`). Телефон присипляє застосунок, сокет тихо вмирає, а
    pusher-js помічав це за 2,5 хв: екрани вважали канал живим, не
    перепитували, і нове не приходило зовсім. Там же
    `activityTimeout` 30 с / `pongTimeout` 10 с — обрив мережі на ходу
    видно за ≤ 40 с, а не за 150.
  - **Докачування — на `pusher:subscription_succeeded`**: цей ключ у
    обробниках `useChannel` спрацьовує на першу підписку й на кожну після
    повторного зʼєднання. RealtimeBridge докачує лічильники, chat-screen
    — свіжу сторінку й шапку (`cancelRefetch: false` — запит, що вже йде,
    не дублюється).
  - **Перепит — лише без каналу**: «живо» — це УСПІШНА підписка, не просто
    зʼєднання (`useRealtimeConnected()` — особистий канал,
    `useChannelLive(name)` — канал екрана). Коли перепит вимикався від
    самого зʼєднання, а підписка не проходила, нове в розмові
    запізнювалось.
  - **Лише WebSocket** (`enabledTransports: ['ws', 'wss']`): запасні
    HTTP-транспорти pusher-js у React Native доставляють із затримкою.
  - **Ключ Pusher памʼятається** (SecureStore, привʼязаний до адреси
    сайту): наступний запуск зʼєднується одразу, не чекаючи
    `/api/pusher/config` (на холодному Vercel — 1–2 с); свіжий ключ
    береться паралельно, змінився — перепідключення.
  - У dev у лог Metro (`[Pusher] …`) пишуться лише збої: канал не
    піднявся, сайт не підписав, «за 5 с підписки немає» (і де застрягло),
    помилка зʼєднання. Звичайна робота мовчить — власник попросив
    прибрати шум із термінала. Ознака, що каналу немає зовсім: нове
    приходить за ≈ половину інтервалу перепиту (2 с у розмові, 4 с у
    списку). Виміряно з каналом: подія доходить за десятки мс після
    запису на сервері.
  - **Канал екрана — `useChannel(name, handlers)`**: підписка, поки екран
    змонтований (з лічильником — двоє екранів на одному каналі не
    відпишуть одне одного), обробники завжди свіжі. Зʼєднання відкриває
    лише RealtimeBridge; хук чекає його й підписується на кожному новому
    (після повторного входу). Підписуємось завжди `subscribe()`, а не
    `channel()`: той повернув би скасовану підписку (вийшов із розмови й
    одразу повернувся), і подій на ній уже не було б.
  - pusher-js у збірці для React Native тягне `@react-native-community/netinfo`
    — він є в Expo Go; не видаляй.
  - **Клас Pusher — `module.exports.Pusher`, не default.** Збірка
    `pusher-js/react-native` 8.6 default не має (хоча типи його
    обіцяють), і `import Pusher from …` давав обʼєкт — `new Pusher`
    падав «Object cannot be used as a constructor», і живого каналу на
    телефоні не було зовсім (усе йшло перепитом). `realtime.ts` бере
    `.Pusher` з фолбеком на default. Оновлюєш pusher-js — перевір, що
    канал піднімається (`[Pusher] зʼєднано за …` у лозі).

  інакше воно розмазувало чіткий край і кут сторінки вгорі (власник);
  грань сторінки — `zIndex` над усім. Варіанти, які власник відкинув: два шари розмиття з майже
  щільним затемненням угорі (зміст зникав, переходи видно), простий
  градієнт без розмиття, щільна заливка з коротким згасанням
  («жорстко»), напівпрозоре скло з чітким краєм
  (було в розмові — там і його прибрали) і майже щільна заливка, під якою
  зміст «обривався» під шапкою. `headerShadowVisible: false` — тло малює
  сам екран (SwipeTabs: один ефект до перемикача включно);
  `headerBlurEffect` — тверда шапка з чітким краєм (розмова; Backdrop):
  суцільний фон і тонка лінія знизу — так само, як у поля внизу
  (ChatComposer), за проханням власника. Те саме
  тло — у смуги пошуку в чатах і у верхньої смуги розмови з Zunor (вона
  теж лежить поверх розмови). Низ: поле розмови з Zunor
  (кнопки-відповіді НАД полем, власник) лежить ПОВЕРХ розмови — над
  полем зміст чіткий до самого краю (згасання над полем власник
  прибрав: текст тьмянів, ще не дійшовши до поля), а прокручене
  заходить ПІД поле й там розмивається й тоне, сильніше до низу екрана
  (`FooterBlur` у `ui/header-fade.tsx` — дзеркало тла шапки). Поле —
  absolute до низу блоку розмови, зміст відступає на його заміряну
  висоту. Під блоком — розпірка `useKeyboardHeight` (висота клавіатури
  мінус смужка «додому», та сама тривалість і крива), а відступ під
  смужку «додому» в поля — ЗАВЖДИ: KeyboardAvoidingView і перемикання
  цього відступу з клавіатурою давали ривок, коли клавіатура ховалась
  (власник). Кнопки-відповіді проявляються по одній зліва направо
  (`chipIn`, 340 мс, крок 70 мс), зникають разом — рівно, без пружин.
  Людина внизу розмови — низ тримається, коли вікно міняє висоту
  (`onLayout` прокрутки → `scrollToEnd` без анімації): з клавіатурою
  розмова їде вгору кадр у кадр, а не ховається під поле. «Надіслати» й
  «Стоп» (`ActionButton` у `zunor/composer.tsx`) — обидві завжди
  змонтовані й перетікають одна в одну прозорістю й масштабом (200 мс):
  заміна монтажем із ZoomIn/ZoomOut «вискакувала» (власник). «Подати пропозицію» на заявці — так само поверх, але
  зі згасанням над кнопкою (`ui/footer-fade.tsx`). Бічні місця шапки — `minWidth`, а не
  `width`: у тісному місці пігулка «Змінити» мірялась стиснутою — колом
  з половиною «З».
  Назва — завжди в самій шапці: на головних екранах розділів із нижньою
  панеллю (клієнт і майстер, `headerTitleAlign: 'left'` у TabStack) —
  ліворуч, 22 pt, і НЕ переїжджає в центр під час прокрутки (власник).
  Лише з системними вкладками майстра (`MASTER_DOCK = false`) — велика
  ліворуч (`useInlineTitles()`), а щойно зміст пішов під шапку
  (`COLLAPSE_AT`) — маленька по центру, як в App Store. Шапка
  знає прокрутку зі спільного значення маршруту (`headerScroll`): екран
  зі своїм списком мусить його оновлювати, як SwipeTabs. На решті й у
  клієнта — назва по центру. Кожен екран зі
  стековою шапкою гортається через `useLargeTitleScroll()`
  (`lib/large-title.ts`: Animated.ScrollView / Animated.FlatList,
  відступ згори, прокрутка → шапці) — інакше зміст заляже під шапку.
  Знизу — `padBottom` (`useContentBottom`, у SwipeTabs — `scroll.padBottom`):
  на iOS кожна вкладка майстра має свій SafeAreaProvider, і `bottom` там
  уже з панеллю вкладок. Без нього кінець списку ховався під панеллю
  (`contentInsetAdjustmentBehavior: 'never'` вимикає системний відступ).
  Список із «потягни, щоб оновити» на iOS відступає через contentInset
  (`shift`) — йому ще `marginBottom: shift` у contentContainerStyle:
  інакше порожній `grow`-зміст вищий за видиму частину, його можна
  підняти, і він відскакує вище свого місця (власник помітив).
  **Порожні стани — посередині ЕКРАНА**, однаково всюди (власник):
  `EmptyState` / `ScreenCenter` (`components/empty-state.tsx`) міряють
  свій блок і зсувають зміст до середини екрана (над клавіатурою, якщо
  вона є). Список із contentInset кладе навколо себе
  `<EmptyStateInset value={shift}>` (SwipeTabs робить це сам);
  перевернутий список розмови — `value={null}` (там середина — область
  повідомлень). Плитка порожнього стану — сіра (`bg-shell`, іконка
  `mutedForeground`), без акценту навіть там, де вона жива: «Поки тихо» в

  прибрати синій дзвіночок).

  «Зареєструватися») стоять унизу на місці й ховаються під клавіатуру.
  Дістати їх — потягнути екран униз (`keyboardDismissMode="on-drag"`;
  прокрутка тому пружинить і з коротким змістом — без руху «потягнули»
  не помітно) або торкнутись порожнього місця.
  Висота — з подій клавіатури (iOS `keyboardWillChangeFrame`: куди й за
  скільки поїде), розпірку веде `withTiming` з тією ж тривалістю й
  кривою (`KEYBOARD_EASING`). Не `useAnimatedKeyboard`: клавіатура
  виїжджає ще під час появи екрана, і він віддавав одразу кінцеву висоту
  — кнопка стрибала (власник помітив). Не піднімати кнопку зсувом із
  замірів onLayout (заміри розійшлись — кнопка лягла на поле пароля), не
  KeyboardAvoidingView і не `automaticallyAdjustKeyboardInsets` (міняють
  відступ із запізненням, поле підскакувало й осідало).
  Поява — усе одразу, без затримок (власник): перехід — проява на місці
  (`animation: 'fade'`, 250 мс, у `_layout`), заголовок і поля водночас
  проявляються й ледь піднімаються (`FadeInDown`, 12 pt, 380 мс,
  timing), а клавіатура в ту ж мить виїжджає знизу й підштовхує
  «Увійти». Поле пошти — `focusOnMount` (ui/text-field): з першого кадру
  вже у фокусі, рамка акценту не «спалахує» потім (власник); курсор — у
  наступному кадрі, коли екран уже слухає клавіатуру. `autoFocus` кликав
  клавіатуру ще до підписки, і кнопка доганяла ривком. Заголовок — як у ClickUp: 28 pt,
  напівжирний, рядки 1.1; «Забули пароль?» — 16 pt напівжирним, сірим.

  `lib/email-domains.ts`), як у ClickUp: почав вводити — «@gmail.com»,
  «@ukr.net», «@icloud.com», «@outlook.com» (порядок — за поширеністю в

  реєстрації, входу, повернення застосунку з фону — і, поки сесії немає,
  знову ставить `isPending: true`. Коли корінь ховав на це весь `Stack`,
  екран реєстрації розмонтовувався разом із переходом на код, і людина
  опинялась на вході (власник помітив); код губився б і після походу в
  Пошту. Не повертати `if (isPending) return null`.

  **Google** (`auth/use-google-sign-in.ts`) —
  `authClient.signIn.social({ provider: 'google' })` плагіна expo:
  системне вікно браузера на сайт → Google → колбек сайту → назад у
  застосунок за схемою (`zunor://`, в Expo Go — `exp://`); сесію
  дописує в адресу повернення плагін `expo()` на сервері (`?cookie=`).
  Сервер для цього вже готовий (провайдер Google, `trustedOrigins`),
  окремого OAuth-клієнта для застосунку немає — редірект у Google той
  самий, що в сайту. Тому вхід через Google працює лише проти сайту на
  https (бойовий, деплой Vercel з `ZUNOR_EXPO_GO=1` для Expo Go): адресу
  повернення `http://192.168…` Google не приймає. Новий акаунт приходить
  без анкети — далі як завжди. Закрите вікно — мовчки; помилка сервера —
  рядок під кнопкою. Кнопка (`auth/google-button.tsx`) — грань `chip`,
  скруглення 16, знак Google ліворуч. Тексти помилок входу — `auth/sign-in-error.ts`.
- **Скелетони — скрізь, де дані вантажаться вперше** (так попросив
  власник), а не спінер: `ui/skeleton.tsx` — `Skeleton` (усе всередині
  «дихає» разом, рівний timing, із «Зменшити рух» — без руху), `Bone`
  (сірий брусок), `SectionSkeleton` (група налаштувань) і
  `SettingsSkeleton` (екран із груп, відступи як у `SettingsScroll`).
  Будова — та сама, що в справжнього екрана, щоб нічого не стрибало, коли
  прийдуть дані. Де: картки «Замовлень» і стрічки (`jobs/card-skeleton`),
  сповіщення, список чатів, розмова (`chat/chat-skeleton`: пузирі, імʼя й
  фото в шапці), заявка (`JobSkeleton` у `job-screen`), розділи
  налаштувань (`QueryGate` → `skeleton` — будова розділу), «Ваші заявки»
  в бічній панелі. Спінер лишається лише на довантаженні наступної
  сторінки в кінці списку й у кнопках. Новий екран з даними — одразу зі
  скелетоном.
- **Назва заявки на її екрані** (`jobs/job-screen.tsx`) — розмір за
  довжиною (`titleType`: ≤ 26 знаків — 26, ≤ 52 — 23, довша — 21, як
  на сайті 26 semibold) і рівні рядки (`ui/balanced-text.tsx`: системного
  `text-wrap: balance` в iOS немає — невидима копія тексту з жорстко
  заданою шириною міряє, скільки рядків на всю ширину, і двійковим
  пошуком знаходить найвужчу ширину з тим самим числом рядків). Не
  брати для цього перший `onTextLayout` самого тексту: iOS може дати
  його з проміжної, вужчої ширини — перша версія через це рвала назву
  на чотири рядки. Обгортка `BalancedText` — завжди на всю ширину: у
  батька з `items-center` вона стискалась до тексту, кожен підбір
  звужував її знову, і текст «смикався» по колу. Дефіс у назві — нерозривний
  (U+2011), щоб «4-» не лишалось у кінці рядка. 30 pt жирним без цього
  ламалось «слово, слово, два слова в кінці» — власник назвав це
  хаосом.
- **Файли в `fetch`.** Глобальний `fetch` у SDK 58 — `expo/fetch`, і
  частину форми у вигляді `{ uri, name, type }` (старий спосіб React
  Native) він не приймає — кидає «Unsupported FormDataPart». Файл у
  `FormData` — лише `new File(uri)` з `expo-file-system`
  (`lib/upload.ts`).
- **Тексти інтерфейсу — українською**, тон теплий і людяний, як на сайті.
  Коментарі в коді — українською, ідентифікатори — англійською.
- **Стиль коду** — `.prettierrc`: одинарні лапки, без крапки з комою.
- Перевірка перед «готово»: `npm run typecheck` і `npx expo-doctor`.

## Expo has changed — do not trust your training data

Expo ships breaking changes every SDK release. APIs you remember are likely renamed, moved, or removed. Before writing any code that touches an Expo, EAS, or React Native API:

1. Read the major version of the `expo` package in `package.json`.
2. Fetch the matching versioned docs: `https://docs.expo.dev/versions/v<major>.0.0/`
3. For anything else, fetch https://docs.expo.dev/llms.txt — an index of all Expo docs with corrections to common LLM misconceptions. Follow its links to the specific page you need; never answer from memory.

## Commands

Use `bunx` instead of `npx` if the project uses bun (`bun.lock` present).

```bash
npx expo install <package>  # ALWAYS use instead of npm/yarn/pnpm/bun add — resolves SDK-compatible versions
npx expo start              # start the dev server
npx expo lint               # lint
npx tsc --noEmit            # typecheck
npx expo-doctor             # diagnose dependency and config issues
npx expo install --fix      # fix incompatible package versions
```

Run lint and typecheck before declaring any task done.

## Navigation & Routing

- Use **Expo Router** for all navigation. Routes live in `src/app/` — every file there is a screen, `_layout.tsx` files define navigators. Keep non-route code (components, hooks, utils) outside `src/app/`.
- Import `Link`, `router`, and `useLocalSearchParams` from `expo-router`.
- Docs: https://docs.expo.dev/router/introduction.md

## Building with EAS

Use EAS to build, sign, and submit the app in the cloud (`eas build`, `eas submit`) and to ship over-the-air updates (`eas update`) — no local Xcode or Android Studio required. Run EAS CLI as `bunx eas-cli <command>` in Bun projects, or `npx eas-cli@latest <command>` otherwise; substitute that for bare `eas` in docs examples.
Docs: https://docs.expo.dev/eas/index.md

## Rules

- If `ios/` and `android/` directories do not exist, they are generated (Continuous Native Generation). Never create or edit them by hand — configure native behavior in `app.json` and config plugins.
- Expo Go only includes its bundled native modules. After adding a library with native code, the app needs a development build: `npx expo run:ios|android` locally, or `eas build --profile development`.
- Prefer recommended Expo modules over third-party libraries, and check your available skills before adding dependencies. Docs: https://docs.expo.dev/versions/latest/index.md
